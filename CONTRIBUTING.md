# Contributing to KeepProof

KeepProof is a privacy-first, production-oriented portfolio project. Contributions are welcome when they keep the main receipt-to-deadline workflow understandable, testable, and usable without a paid external service.

By participating, you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report vulnerabilities through the private process in [SECURITY.md](SECURITY.md), never through a public issue.

## Before you start

Search existing issues and pull requests first. For a behavior change that affects the API, data model, privacy boundary, or architecture, open a focused feature request before investing in a large patch. Small fixes with an obvious scope can go directly to a pull request.

Never put real receipts, names, email addresses, order numbers, signed URLs, credentials, or production logs in the repository. Tests and screenshots must use the synthetic fixtures under `tests/fixtures` or data generated by factories.

## Development environment

The supported path uses Docker Compose, Docker Engine with Compose v2, Git, and Make:

```bash
cp .env.example .env
cp apps/backend/.env.example apps/backend/.env
cp apps/frontend/.env.example apps/frontend/.env
make setup
make up
make seed
```

Open the application at `http://localhost:8080`. Configuration values in the example files are local-only defaults; do not reuse them in a deployed environment.

Useful commands:

```bash
make test
make quality
make e2e
make production-build
make logs
make down
```

`make reset` permanently removes the project's local named Docker volumes. Back up anything you need before running it.

For a narrow feedback loop, run commands in the relevant container:

```bash
docker compose run --rm backend php artisan test --filter=TenantIsolation
docker compose run --rm backend vendor/bin/pint --test
docker compose run --rm backend vendor/bin/phpstan analyse --no-progress --memory-limit=1G
docker compose run --rm --workdir /workspace/packages/deadline-engine backend composer check
docker compose run --rm frontend npm run test:unit
docker compose run --rm frontend npm run typecheck
```

## Design and implementation expectations

- Keep Laravel as the application boundary and the Deadline Engine framework-independent.
- Prefer explicit actions, policies, request objects, resources, enums, and value objects over decorative abstraction layers.
- Preserve household scoping at the trusted backend layer. A hidden frontend control is not authorization.
- Store money as integer minor units, dates in explicit types, and timestamps in UTC with user timezones at display and scheduling boundaries.
- Treat receipt files, OCR text, extraction output, and provider responses as untrusted input.
- Keep external AI optional, consent-based, schema-validated, redacted where configured, and disabled by default.
- Update the OpenAPI contract and generated frontend client in the same change as an API contract update.
- Add an ADR when a decision creates a durable architectural constraint or reverses an accepted decision.
- Avoid unrelated cleanup in a focused pull request.

PHP code uses strict types where applicable, PSR-4, Laravel Pint, and Larastan. Frontend code must pass Prettier, ESLint, Vue TypeScript checks, Vitest, and the production Vite build.

## Tests

Add coverage at the lowest useful layer, then add an integration or end-to-end test when the risk crosses a boundary.

Changes to authorization, account deletion, exports, uploads, document state transitions, job retries, notification deduplication, or deadline calculations require regression tests. Date logic should include table-driven boundary cases. UI changes should cover validation and error behavior; critical flows should remain keyboard-operable and pass the accessibility smoke checks.

Do not weaken assertions, types, audit thresholds, or security validation to make a build pass. If a check cannot be run locally, state exactly which check was omitted and why in the pull request.

## Commits and pull requests

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) with a useful scope when one is clear:

```text
feat(api): add claim package export
fix(processing): make extraction retry idempotent
test(security): cover cross-household document access
docs(ops): document point-in-time restore
chore(deps): update frontend development dependencies
```

Use `!` and a `BREAKING CHANGE:` footer for an incompatible public API, configuration, or data-contract change. Commit messages and all public repository content must be in English.

Keep commits reviewable and do not rewrite shared history. A pull request should explain the problem, trade-offs, exact verification commands, security/privacy impact, migration and rollback considerations, and UI evidence where applicable. The pull-request title should also follow Conventional Commits because it may be used as the squash commit.

## Versioning and releases

KeepProof uses Semantic Versioning. Before `1.0.0`, a minor version may contain a deliberate breaking change, which must still be documented. Maintainers prepare a release by updating [CHANGELOG.md](CHANGELOG.md), running the full quality suite, and creating a signed `vMAJOR.MINOR.PATCH` tag. The artifact workflow builds source archives, image metadata, and SBOMs; it does not publish containers or create a release automatically.
